# v1.2 vendor helpers: which sources rebuild the shipped files

The v1.2 vendor image (`vendor_b`, release `v1.2-android15`) ships four tools besides
`tt_idle_dim`. This page records, for each one, the sha256 read from the running panel and
whether the source in [`services/vendor-helpers/`](../services/vendor-helpers/) reproduces it.

All four files were copied out of the running panel's read-only vendor image and hashed there and
again after transfer; the two agree.

## tt_touch_bind.sh — identical

`sha256 dc890231aae03836cf3c4b6e4715846f495b7bc4b7c43ebec0effdfe112edd3e`

The shipped file is a shell script, so the source and the artefact are the same bytes.
`services/vendor-helpers/touch-bind/tt_touch_bind.sh` hashes to that value.

## tt_idle_peripheral — rebuilds byte for byte

`sha256 9c9871ae8d1db25b520bdfde9ada6eed90a5c6674a9dd3dbc19a7ce50c31e864`, 9,688 bytes

Rebuilt from `idle-peripheral/idle_can.c` and `idle_frames.h` with the repository's own
freestanding startup shim, using the NDK clang that ships in this build tree:

```sh
ROOT=~/android15-build/imx-android-15.0.0_1.2.0/android_build
$ROOT/prebuilts/clang/host/linux-x86/clang-r536225/bin/clang \
  --target=aarch64-linux-android35 --sysroot=$ROOT/out/soong/ndk/sysroot \
  -O2 -fPIE -pie -nostartfiles -Wl,-e,_start \
  -o tt_idle_peripheral \
  services/tt-idle-dim/crt0.S services/tt-idle-dim/crt_glue.c \
  services/vendor-helpers/idle-peripheral/idle_can.c
```

The output is 9,688 bytes with sha256 `9c9871ae…`, identical to the shipped file. Note that the
build is **PIE, not static**: `-static` fails against this sysroot (`unable to find library -lc`),
and the shipped binary is a PIE executable.

## tt_misc_writer — source present, not rebuilt here

`sha256 42b1040bd1e85aeece6be7397549a8909c2c4cef06e621bd271bda7bbe25d3aa`, 67,448 bytes

The source is `avbab/avbab.c` with its Soong module in `avbab/Android.bp`. It is the same source
the system image also builds as `/system/bin/avbab`; the two binaries differ (different build
configuration), so the system copy's hash is not evidence either way.

Rebuilding it needs an AOSP tree with Soong, which is not in this checkout: a standalone NDK
compile of `avbab.c` does not link. Until that run happens, the source is the best available
record and the hash above is what a rebuild must match.

## tt_reboot_pin.ko — source present, not rebuilt here

`sha256 b0114f007bad00b392aba788f7cd19bb5a671c5fb46a0b28c0bd360908e12a0e`, 105,896 bytes

The source is `reboot-pin/tt_reboot_pin.c` (`make -C $KERNEL_OBJ M=$PWD modules`). The shipped
module identifies itself as:

```
description: Restore GPIO1_IO02/WDOG1_WDOG_B on the normal reboot path only
vermagic:    6.6.58-4k-ga9e7dfe9bde2 SMP preempt mod_unload modversions aarch64
```

which matches what the source does and pins the kernel it was built against. Reproducing it byte
for byte needs that kernel's build tree with its config and toolchain; the module's vermagic will
differ from any other build, so a rebuild is only comparable against the same kernel revision.

## What this means for rebuilding the release

`tt_idle_peripheral` and `tt_touch_bind.sh` can be reproduced from this repository today. The
other two have their sources recorded; their builds need the Soong tree and the vendor kernel
tree respectively.
